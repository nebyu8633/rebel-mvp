# LifeOS — ניהול חיים ומטרות

אפליקציית ווב אישית (עברית, RTL) שמחברת מטרות שנתיות לאבני דרך, יעדים חודשיים ושבועיים, ומשימות יומיות — עם לוח שנה, שגרות חוזרות, הרגלים, תפריט ורשימת קניות, מעקב פיננסי ידני ועוזר תכנון.

> התיקייה הזו עצמאית. הקובץ `app.py` בשורש המאגר הוא פרויקט Streamlit אחר ולא נגעתי בו.

## מה יש באפליקציה

## הפעלה מקומית

דרישות: Node.js 20 ומעלה.

```bash
cd lifeos
npm install
npm run dev        # http://localhost:3000
```

בלי שום הגדרה האפליקציה רצה ב**מצב מקומי**: משתמש יחיד, ללא התחברות, הנתונים נשמרים ב-`localStorage` של הדפדפן ושורדים רענון — אבל לא ניקוי נתוני אתר, ולא מסתנכרנים בין מכשירים. בהגדרות ← נתונים יש ייצוא/ייבוא גיבוי JSON.

פקודות נוספות:

```bash
npm test                      # 108 בדיקות יחידה (Vitest)
npm run lint                  # בדיקת טיפוסים
npm run build && npm start    # בנייה והרצה לפרודקשן
./scripts/test-migration.sh   # מריץ את שתי המיגרציות על PostgreSQL מקומי זמני ובודק RLS, אטומיות ונעילת גרסאות (דורש PostgreSQL 15+)
```

## משתני סביבה

מעתיקים את `.env.example` ל-`.env.local`:

| משתנה | חובה? | הסבר |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | לא | כתובת פרויקט Supabase. יחד עם המפתח הבא — מפעיל התחברות ושמירה בענן |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | לא | המפתח הציבורי (anon). כל הגישה מוגבלת ע״י RLS |
| `ANTHROPIC_API_KEY` | לא | **שרת בלבד** (בלי `NEXT_PUBLIC_`). מפעיל את תכנון ה-AI והעוזר |
| `ANTHROPIC_MODEL` | לא | ברירת מחדל `claude-opus-5-5` |

אין שימוש במפתח service-role בשום מקום, ומפתח ה-AI לא נשלח לדפדפן.

## הגדרת Supabase (שמירה בענן + התחברות)

1. יוצרים פרויקט ב-[supabase.com](https://supabase.com).
2. מריצים את המיגרציות לפי הסדר: ב-SQL Editor מדביקים את `supabase/migrations/20261031000000_init.sql` ואחר כך את `20261101000000_goal_planning.sql`, או עם ה-CLI: `supabase link` ואז `supabase db push`.
3. ב-Authentication ← Providers משאירים Email פעיל. ב-URL Configuration מוסיפים את כתובת האתר ואת `<site>/auth/callback` כ-Redirect URL.
4. ממלאים את שני משתני ה-`NEXT_PUBLIC_SUPABASE_*` ומפעילים מחדש.

מה מקבלים: כל דף דורש התחברות (middleware), כל טבלה עם `user_id` ומדיניות RLS שמאפשרת לכל משתמש לקרוא/לכתוב רק את השורות שלו (נבדק בסקריפט על PostgreSQL אמיתי, כולל ניסיונות גישה בין משתמשים). אין מעבר אוטומטי של נתונים ממצב מקומי — משתמשים בייצוא/ייבוא גיבוי.

**שקיפות:** סכמת ה-SQL וה-RLS נבדקו על PostgreSQL 16 מקומי, וההתאמה בין הסכמה למודל הנתונים נבדקת בבדיקות. שכבת ה-Supabase באפליקציה (התחברות, PostgREST) **לא נבדקה מול פרויקט Supabase אמיתי** בסביבת הפיתוח הזו, כי לא היו פרטי גישה.

## הגדרת AI (Anthropic)

מגדירים `ANTHROPIC_API_KEY` בשרת. השירות (`src/lib/ai/`):
- רץ בצד השרת בלבד, דרך ממשק ספק (`AIProvider`) שמאפשר להחליף ספק;
- מבקש פלט JSON מובנה (structured outputs) לפי סכמת Zod, ואז מריץ בדיקות תקינות של האפליקציה (תאריכים בטווח, משכים, תלויות לא מעגליות, מספר משימות) לפני שמשהו מוצג;
- מטפל בשגיאות (מגבלת קצב, מפתח שגוי, תקלה, סירוב) ומציג אותן — **לעולם לא ממציא תשובה מוצלחת כשהקריאה נכשלה**; המשתמש יכול לבחור במפורש לעבור למנוע הבסיסי;
- כולל הגבלת קצב פשוטה לכל משתמש (12 בקשות לדקה, בזיכרון של כל מופע שרת);
- מפעיל `fallbacks: "default"` של ה-API: אם המודל מסרב מטעמי בטיחות, ה-API מנסה מודל חלופי בעצמו.

העוזר שולח לשרת תמונת מצב מצומצמת של הנתונים של המשתמש עצמו; בענן, הנתונים נקראו דרך RLS והנתיב דורש אותה התחברות.

**בלי מפתח** הכול ממשיך לעבוד: המתכנן משתמש בתבניות שקופות (אופנוע — רק אחרי שהוזנו דגם, מחיר, חיסכון ויכולת חיסכון; משקל — רק אחרי אישור משקל התחלתי; תיק — לא ממציא שווי נוכחי), והעוזר עונה על השאלות הנפוצות בכללים מעל הנתונים. התשובות מסומנות ״מנוע בסיסי (ללא AI)״.

הקריאות ל-API נבדקו עם תעבורה מדומה (mock) בבדיקות היחידה; **לא בוצעה קריאה אמיתית ל-API** כי לא היה מפתח בסביבת הפיתוח.

## תכנון מטרה בשיחה

**הזרימה:** המטרות שלי ← ״+ מטרה חדשה״ ← מתארים את המטרה במילים שלכם ← שיחת תכנון ← עמוד התוכנית ← ״אישור התוכנית והוספה ללוח השנה״.

- **השיחה** (`/goals/<id>/chat`): שאלה אחת בכל פעם, עם כרטיסי בחירה, בחירה מרובה, מספר/סכום, תאריך, ימים בשבוע ותשובה חופשית. פרטים שכבר נאמרו בתיאור (למשל ״10 קילו בתוך שנה״) לא נשאלים שוב. מספרים אפשר לסמן כ״הערכה״. מדלגים רק על שאלות שאינן קריטיות, ומה שדולג נרשם כשאלה פתוחה.
- **שמונה שלבים** מוצגים למעלה. שלב שלא רלוונטי למטרה פשוט לא נשאל.
- **סיכום התשובות** בצד: כל פרט מסומן כ״אושר״, ״הערכה״, ״הנחה״ או ״המלצה״. אפשר לערוך כל תשובה או לאשר הנחה.
- **שמירה ושחזור:** כל צעד נשמר באופן אטומי (הודעות, פרופיל ומצב השיחה). אפשר לצאת ולחזור בכל שלב, ולכל מטרה יש שיחה משלה.
- **כמה מטרות בתיאור אחד** מזוהות, ומוצע ליצור אותן בנפרד. הן חולקות את אותו לוח שנה ואותה מגבלת זמן.
- **סתירות** (למשל יעד נמוך מהמצב הנוכחי, קצב חיסכון שלא מספיק) מוצגות בשיחה.

**התוכנית** (`/goals/<id>/plan`) כוללת: סיכום, תוצאה רצויה, נקודת התחלה, תאריך יעד, מדדי הצלחה, אסטרטגיה ונימוק, ציר אבני דרך, יעדים חודשיים, תוכנית ביצוע שבועית, משימות (משך, מועד, דדליין, עדיפות, תלויות, תזכורת), שגרות חוזרות (ימים, יום גיבוי כחלופה ולא כמפגש נוסף, שעה), משאבים, סיכונים, הנחות ושאלות פתוחות, מדדי תוצאה בנפרד ממדדי פעילות, ובדיקת התקדמות שבועית.

- **טיוטה מול פעילה:** אפשר לערוך את הטיוטה בכל פרט. גרסה מאושרת היא תמונת מצב קבועה, ובענן הנעילה נאכפת גם במסד הנתונים. עריכה של תוכנית פעילה יוצרת גרסה חדשה.
- **אישור:** בדיקת תקינות ← שמירת הגרסה ← אבני דרך, יעדים, משימות, משימות חוזרות ותזכורות — הכול בפעולה אטומית אחת. אם משהו נכשל לא נשמר כלום ומוצגת שגיאה, לא הודעת הצלחה. מזהי הרשומות נגזרים מהמטרה ומהתוכנית, ולכן ניסיון חוזר לא יוצר כפילויות.
- **אותן רשומות בכל מקום:** המשימות שנוצרות הן משימות רגילות של האפליקציה, מקושרות למטרה, לאבן הדרך ולגרסת התוכנית. הן מופיעות בלוח השנה, ב״היום שלי״, ברשימת המשימות ובעמוד המטרה.
- **עדכון תוכנית פעילה:** לפני האישור מוצגת תצוגה מקדימה של מה יתווסף, יעודכן ויוסר. משימות שהושלמו לא משתנות, סדרה שמשנים בה ימים שומרת את המופעים שהושלמו, ומשימה שהזזתם ידנית בלוח שומרת את המועד שבחרתם.
- **שיבוץ:** לפי דדליינים, תלויות, משך, הזמינות היומית (עם מרווח של 20%), השעות השבועיות למטרה, אירועים קיימים, משימות של מטרות אחרות, ימים ושעה מועדפים. משימות לא מוקדמות לפני הזמן.
  - בלי מידע על זמינות, המשימות מוצעות בלי תאריך ביצוע.
  - כשיש עומס מוצגות חלופות (להאריך את המועד, להוריד משימות בעדיפות נמוכה, להגדיל שעות, לחשוב מחדש על היקף המטרה), ולפני אישור עם עומס נדרש אישור מפורש.
- **התקדמות:** עמוד המטרה מציג בנפרד את ביצוע המשימות ואת ההתקדמות במדד עצמו (משקל, שווי תיק, חיסכון, או מדד שמעדכנים ידנית), יחד עם הפעולה הבאה המומלצת ומועד בדיקת ההתקדמות הבאה. אחוז מוצג רק כשיש נתונים מדידים.

**AI מול מנוע בסיסי:** בלי מפתח AI, השיחה מתנהלת עם מנוע מובנה: בנק שאלות מותאם לכל סוג מטרה (משקל, תיק השקעות, רכישה/אופנוע, הכנסה, למידה, מטרה כללית), עם שאלות המשך שתלויות בתשובות ותבניות תוכנית שקופות. עם מפתח AI, השרת מבקש מהמודל את התור הבא ואת התוכנית בפלט מובנה, ומאמת אותם לפני שהם מוצגים:
- עובדה שהמודל סימן כ״מאושרת״ אבל אי אפשר לקשר אותה להודעה של המשתמש מורדת ל״הנחה״.
- התוכנית עוברת את אותה בדיקת תקינות כמו תוכנית מהמנוע הבסיסי.

אם קריאה ל-AI נכשלת, מוצגת שגיאה עם ״ניסיון חוזר״ ו״המשך עם המנוע הבסיסי״. השיחה נשמרת. התשובה מוצגת אחרי שהמודל מסיים לכתוב אותה (ללא הזרמה בזמן אמת).

## תזכורות והתראות — מה עובד ומה לא

- תזכורות בתוך האפליקציה + התראות דפדפן (אחרי מתן הרשאה), לפי אזור הזמן שהוגדר.
- כל תזכורת נשלחת פעם אחת בלבד (יומן ״נשלח״ משותף לכל הלשוניות).
- לכל משימה אפשר להגדיר כמה תזכורות: לפני ההתחלה, לפני הדדליין, או בתאריך ושעה. אפשר לכבות תזכורת בודדת, ולהשתמש ב״נודניק 10 דק׳״ (שנשמר במכשיר).
- **בלי Web Push:** התזכורות פועלות רק כשהאפליקציה פתוחה בלשונית כלשהי. תזכורת שהוחמצה ביותר מ-10 דקות לא מוצגת בדיעבד.
- **Web Push (התראות כשהאפליקציה סגורה):** ממומש, ופועל רק כשכל ההגדרות קיימות:
  1. מצב ענן (Supabase).
  2. מפתחות VAPID: `npx web-push generate-vapid-keys`, ואז `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`.
  3. `SUPABASE_SERVICE_ROLE_KEY` — בשרת בלבד, משמש רק את נתיב התזמון.
  4. `CRON_SECRET`.
  5. מתזמן שקורא ל-`GET /api/cron/reminders` כל כמה דקות עם הכותרת `Authorization: Bearer <CRON_SECRET>`. ב-Vercel Pro מוסיפים ל-`vercel.json` את `{"crons":[{"path":"/api/cron/reminders","schedule":"*/5 * * * *"}]}` (Vercel שולחת את הכותרת לבד כש-`CRON_SECRET` מוגדר). בתוכנית החינמית של Vercel מותר רק תזמון יומי, ולכן צריך מתזמן חיצוני (למשל cron-job.org).

  כל תזכורת נשלחת פעם אחת: המשלוח נרשם בטבלת `push_deliveries`. במסך ההגדרות מופיע ״לא פעיל״ ומה חסר כל עוד ההגדרה לא שלמה. **החלק הזה לא נבדק מול שירות Push אמיתי**, כי בסביבת הפיתוח אין מפתחות ואין פרויקט Supabase. החלק שבוחר אילו תזכורות לשלוח נבדק בבדיקות יחידה. ב-iOS התראות עובדות רק לאתר שהותקן למסך הבית.
- לא נוצרות שעות לארוחות או תזכורות שלא הגדרתם.

## החלטות מודל ונתונים

- **מקור אמת אחד למשימות.** לוח השנה, רשימת המשימות ו״היום שלי״ קוראים וכותבים את אותן רשומות.
- **משימות חוזרות** נשמרות כחוק חזרה אחד; כל מופע מחושב לפי תאריך. מופע שנגעו בו נשמר ברשומה עם מזהה דטרמיניסטי `<task>:<date>` (ייחודי גם במסד) — כך מופע לא יכול להשתכפל. נתמכים: יומי/שבועי/חודשי, מרווח, ימים בשבוע, תאריך התחלה וסיום, מספר מופעים, השהיה, ביטול מופע בודד, עריכת מופע בודד או כל הסדרה, ומדיניות פספוס (נשאר באיחור / דילוג / מעבר ליום גיבוי). השלמות עבר נשמרות גם אחרי שינוי הסדרה.
- **תאריכים ו-DST:** חישובי לוח שנה על מחרוזות `YYYY-MM-DD` (בלי חשבון מילישניות), והמרה לשעה אמיתית רק דרך אזור הזמן — נבדק על מעברי שעון ישראל וארה״ב.
- **פיננסים:** החיסכון לאופנוע והתיק הם חשבונות נפרדים. רישומים: הפקדה, משיכה, ״עדכון שווי/יתרה״. בתיק מוצג שינוי השוק בנפרד מההפקדות; ההפקדה החודשית הנדרשת מוצגת בארבעה תרחישים (0%, 2%, 5%, 8%) — כולם מסומנים כהנחות להמחשה בלבד. אין חיבור לבנק או ברוקר.
- **התאוששות ממשימות שפוספסו:** פריסה לפי חשיבות וזמן פנוי בשבוע הקרוב (לא הכול למחר), דילוג על מופעים של שגרות, החזרה ל״ללא תאריך״ של משימות בעדיפות נמוכה שלא נכנסות — והכול מוצג לאישור.
- **אין ציון כולל** לחיים; כל מדד מוצג בנפרד, ואם חסר נתון — כתוב מה חסר במקום מספר מומצא.

## מבנה

```
lifeos/
  src/app/              דפים (App Router) ו-API (/api/ai/*)
  src/components/       רכיבי UI
  src/lib/              לוגיקה: types (Zod), recurrence, tasks, finance, grocery, goals,
                        habits, recovery, reminders, planner/, ai/, store/ (local + Supabase)
  src/lib/__tests__/    בדיקות יחידה
  supabase/migrations/  סכמת SQL + RLS
  scripts/              בדיקת המיגרציה על PostgreSQL מקומי
```

סטאק: Next.js 15, React 19, TypeScript, Tailwind CSS 4, Zustand, Zod 4, Supabase (`@supabase/ssr`), Anthropic SDK, Vitest.

## מגבלות ידועות

- גרירה בלוח השנה עובדת בעכבר; במסך מגע מזיזים דרך ״תזמון מחדש״ בתפריט המשימה.
- אין סנכרון ליומן חיצוני (Google/Outlook); הלוח עובד עצמאית.
- אין מעבר נתונים אוטומטי ממצב מקומי לענן (יש ייצוא/ייבוא).
- הגבלת הקצב ל-AI היא בזיכרון של כל מופע שרת, לא גלובלית.
